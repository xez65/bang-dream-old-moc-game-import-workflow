# bang dream 老模游戏向导入使用方案

## 项目介绍
B站无影手爱音出品
本项目旨在解决bang dream老式的moc模型因格式问题无法导入游戏引擎进行使用，给创作者的灵感落地带来很大限制，本项目的工作流导入agent进行扫描学习后，可将包含”改模“在内的所有moc模型重绘并优化成moc3后缀的模型，供制作者导入游戏进行使用

本仓库提供一套可复核的 Cubism 2 `.moc` 到 Cubism 3 `.moc3` 的迁移工作流。它把源资源盘点、运行时语义核验、模型合并、目标资源生成、Unity 验收、确定性打包和证据交付拆成独立阶段，帮助创作者把旧模型迁移到游戏引擎可使用的运行资源。

## 重要边界

这份发布包是工作流规范和案例证据边界的整理，不是一个已经参数化完成的一键转换器。当前包没有跨角色自动编排器；新角色必须从自己的源清单建立数量、身份、坐标、参数范围和测试计划。流萤猫只作为实际迁移案例，案例中的数量、路径、阈值和本机环境不能直接套用。

“模型文件生成成功”“静态外观通过”“动作全量播放”“物理响应”“Unity 运行验收”“压缩包完整”和“用户认可”分别记录，任何一项都不能替代另一项。没有证据的因果解释保持未定因。

## 工作流阶段

完整迁移按 G0 到 G8 执行：

- **G0 源盘点与身份冻结**：列出归档条目和哈希，追踪所有入口、唯一 rig、参数、Part、drawable、deformer、动作和表情。
- **G1 可信源基线与多入口归属**：使用源运行时建立受控基线，通过 drawable、父 deformer、Part、纹理页和几何证据确认部件归属。
- **G2 源运行时语义与目标侧车**：实测缺失参数、缺失 Part、越界样本和结束时刻；保留未知记录，单独记录目标侧裁剪。
- **G3 单角色合并与版本适配**：按实际 reference MOC3 版本 lowering 和 bake，核对几何、UV、全局 renderOrder、遮罩、blend 和配件变换。
- **G4 运行资源冻结**：从 model3 入口解析引用闭包，逐文件建立运行资源清单和 SHA-256。
- **G5 Unity 净室与运行前检查**：隔离工程、逐文件核对导入结果，先编译生成后的探针副本，再验证控制器、fade 表、动画事件和资源身份。
- **G6 真实 PlayMode 动态验收**：全量核对动作和表情身份、时序、回调、参数和顶点有限值；另行记录姿势、物理和截图覆盖。
- **G7 确定性打包与最终文件回读**：固定排序、时间戳和压缩属性，双次构建并从最终磁盘 ZIP 回读 CRC、路径、清单、哈希和引用闭包。
- **G8 证据网页与交付检查**：回读内联图片、镜像、浏览器加载、截图、有效链接和负例，无法执行的检查保持未验证。

## 推荐阅读顺序

1. 先读本文，确认适用范围、证据边界和发布包文件。
2. 再读 `docs/moc2-to-moc3-workflow-v2.md`，按 G0–G8 建立本轮输入清单、输出目录和证据计划。
3. 遇到缺件、错层、白块、UV、动作接线、ZIP 或浏览器问题时，查 `docs/moc2-to-moc3-pinhao-lessons-20261005.md` 的对应故障分支。
4. 需要复用脚本或复跑测试时，查 `docs/tools-README.md`，先核对脚本当前接口和输入输出，不按文件名推断通用性。

## 拿到工作流包后的配置

这是文档、案例和工具索引包，不是可直接打开的 Unity 工程。包内不包含 Cubism SDK、第三方模型、贴图、Unity 工程、`.env` 或密钥。其他用户使用时，应为自己的角色建立新配置和新输出目录：

```text
角色标识: <角色名>
源归档: <源 zip 或目录>
入口清单: <全部 model.json 或其他入口>
暂存根目录: <ASCII 路径，并保留原路径映射>
输出根目录: <本轮新的日期目录>
目标 MOC3 reference: <实际版本>
Unity: 6000.5.8f1（案例基线；不同版本要重新验证）
Cubism SDK/Core: <版本或 SHA-256>
转换器/JDK/Python/Node: <实际版本和用途>
目标验收: <动作、表情、姿势、物理、截图范围>
```

配置时不要复制生产者机器的绝对路径或本地 `file:` Package Manager 缓存。Unity 依赖应由接收者自己的 Package Manager 和授权 SDK 目录提供；需要 Umamo/Gradle 时按本轮实际工具使用 JDK 21 基线。中文归档路径可以映射到 ASCII 暂存目录，但必须逐项保存 `archive_path → staged_path` 映射。

## 其他用户拿到 runtime ZIP 后的使用步骤

1. 先阅读 ZIP 内的 `README.txt`、`MANIFEST.sha256` 和 `<角色>.model3.json`，核对入口、资源哈希和候选状态。
2. 安装与记录一致的 Unity Editor 和 Cubism SDK for Unity。流萤猫案例使用 Unity `6000.5.8f1`；换版本或 SDK 后不能沿用生产者的运行结论。
3. 创建隔离 Unity 工程，通过 Package Manager 安装自己的依赖，把运行资源复制到 `Assets/Live2D/Models/<角色名>/`，保持 model3、moc3、贴图、motions、expressions、physics 和 display info 的相对路径。
4. 等待 Cubism importer 生成模型资产、Prefab、动作、表情和 fade 列表；把 README、manifest、证据页和报告放在工程外或 `Documentation/`。
5. 将生成的角色 Prefab 放入场景，配置相机和背景，检查 `CubismModel`、Renderer 纹理、参数数组、MotionController、表情控制器和 Physics 绑定。运行时代码动态加组件后，按 SDK 要求执行 Refresh。
6. 先做一个动作、一个表情、一个默认姿势和 physics on/off smoke test，再按 G5/G6 做全量 PlayMode 验收，保存 Unity、SDK、工程依赖和实际加载资源的版本及哈希。
7. 单独记录包完整性、Unity 导入、控制器接线、动作表情播放、物理响应、视觉对照和用户认可。`unity_verified` 只表示生产者环境下的证据，不能替代接收者自己的 Unity 验证。

遇到缺件、错层、白块、UV、参数别名、动作裁剪、fade 空槽、ZIP 回读或证据页面问题时，按主文档的 G0–G8 阶段恢复；旧候选和旧报告保持冻结，新尝试使用新的日期目录和后继工具。

## 最低证据要求

每轮迁移至少应保存：

- 源归档、入口、唯一 rig、模型和贴图的路径、字节数与 SHA-256。
- 实际引擎、SDK/Core、转换器、JDK、依赖和目标版本。
- 全部源动作和表情的身份、原始字节或逐记录哈希、未知 ID 去向。
- 目标 model3 引用闭包、运行资源逐文件清单和缺失项结论。
- 源参考与目标静态图的姿势、视口、背景、采样时刻和模型哈希。
- Unity 编译、导入、PlayMode、动作、表情、物理和截图报告，按实际覆盖分别记状态。
- 最终 ZIP 的双次构建结果、最终磁盘回读结果、CRC、条目清单和逐文件 SHA-256。

## 复用原则

- 新模型从源清单重新计算数量，不能沿用流萤猫的入口数、参数数、动作数、表情数或坐标。
- 未知参数和未绑定曲线保留原名和原始记录，不猜别名、不静默删除、不自动宣称视觉生效。
- 源运行时行为、目标播放裁剪、结构绑定、值正确、网格响应和像素响应分开记录。
- 诊断渲染器的限制不能反向改写模型；若静态检查与可信图像对照冲突，应回查判据和渲染包装。
- 旧包、旧报告和旧工具保持冻结；新行为使用后继工具和新的输出目录。
- 包完整性、外观认可、Unity 运行时实测和用户验收是独立结论。
